# Мультиплатформа: варианты и принятое решение

## Решение

Выбран **вариант А — общая кодовая база на Rust**, с поддержкой macOS, Windows
и Linux (X11). Приложение переписано; прежняя Swift-версия лежит в `swift/`.

Что получилось на деле:

- Общий код — физика, отрисовка, главный цикл, настройки. Платформенный — по
  одному модулю в `src/platform/` (150–250 строк каждый) и две реализации меню
  в `src/tray.rs`.
- Отрисовка — wgpu: Metal на macOS, DirectX 12 в Windows, Vulkan или OpenGL в
  Linux.
- Версии для Windows и Linux проверены только компилятором; вживую они ещё не
  запускались.
- Linux поддерживается только через X11: Wayland не даёт узнать положение
  чужих окон.

Ниже — исходный разбор вариантов, по которому принималось решение. Оценки в
нём сделаны до переписывания.

## Исходная задача

Как добавить версию для Windows.

## Исходная точка

Сейчас приложение — один файл `main.swift` для macOS. Его можно условно
разделить на три части:

| Часть | Объём | Переносимость |
| --- | --- | --- |
| Физика (`Sim`, `Particle`, `Surface`) | ~250 строк | Логика независима от ОС, но написана на типах CoreGraphics (`CGFloat`, `CGRect`, `CGPath`) |
| Отрисовка и окно-оверлей | ~100 строк | Только macOS: AppKit, Core Animation |
| Список окон, Dock, меню в строке меню | ~100 строк | Только macOS: `CGWindowList`, Accessibility, `NSStatusItem` |

В Windows есть аналоги всего нужного:

- прозрачное окно поверх всех, пропускающее клики
  (`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST`);
- список окон с рамками (`EnumWindows` + `DwmGetWindowAttribute`);
- положение курсора (`GetCursorPos`);
- значок в трее (`Shell_NotifyIcon`);
- прямоугольник панели задач — без каких-либо разрешений, проще, чем Dock.

## Вариант А. Общая кодовая база на Rust

Всё приложение переписывается на Rust. Физика, отрисовка и меню в трее общие;
под каждую ОС — небольшой модуль (список окон, Dock / панель задач).

**За**

- Одна кодовая база, общего кода около 85 %; правка физики делается один раз.
- Одна команда сборки (`cargo build`) на обеих ОС, один набор зависимостей.
- Готовые кроссплатформенные библиотеки для окна, трея и отрисовки.
- Легко добавить сборку под обе ОС в GitHub Actions.
- Дорога к Linux остаётся открытой (с оговорками по Wayland).

**Против**

- Работающую mac-версию приходится переписать и заново отладить.
- Отрисовка меняется: вместо Core Animation — свой рендер (GPU или
  программный); потребление CPU и вид сглаживания нужно будет проверять заново.
- Появляются внешние зависимости и заметно более тяжёлая сборка; сейчас их нет.
- Нужен установленный Rust; бинарник крупнее.
- Dock через Accessibility всё равно остаётся отдельным mac-кодом.

## Вариант Б. Два отдельных приложения

Mac-версия остаётся на Swift без изменений. Для Windows пишется второе
приложение на C# (WPF или WinForms + Win32), физика переносится вручную.

**За**

- Mac-версию не трогаем — она уже работает.
- Каждое приложение использует родные средства своей ОС, без прослоек.
- Нет общих зависимостей; сборка каждой версии проста.
- Самый быстрый путь к первой рабочей Windows-версии.

**Против**

- Общего кода нет: ~250 строк физики дублируются на двух языках.
- Каждую правку физики и каждую новую возможность нужно вносить дважды;
  версии со временем начнут расходиться в поведении.
- Два инструмента сборки, два набора знаний.

## Вариант В. Общее ядро физики + родные оболочки

Физика выносится в библиотеку на C или Rust с C-интерфейсом; оболочки остаются
родными (Swift на macOS, C# на Windows).

**За**

- Физика общая, поведение гарантированно одинаковое.
- Отрисовка на macOS остаётся на Core Animation, как сейчас.

**Против**

- Самая сложная сборка: три языка и склейка между ними.
- Для ~250 строк физики это избыточно: склейки выйдет почти столько же,
  сколько самой физики.

## Сравнение

| | А. Rust | Б. Два приложения | В. Общее ядро |
| --- | --- | --- | --- |
| Общий код | ~85 % | нет | только физика |
| Mac-версию переписывать | да | нет | частично |
| Правка физики | один раз | дважды | один раз |
| Сложность сборки | средняя | низкая | высокая |
| Внешние зависимости | есть | нет | минимум |

## Предварительная рекомендация

Вариант А, если Windows-версия нужна всерьёз и приложение будет развиваться:
оно маленькое, переписать его недорого, а дублирование потом обойдётся дороже.
Вариант Б — если Windows нужна «один раз и забыть».

## Что учесть при любом варианте

- **Проверка.** Windows-версию нужно запускать на Windows-машине; на Mac можно
  проверить только то, что она компилируется.
- **Высокий DPI и несколько мониторов.** В Windows масштаб задаётся отдельно
  для каждого монитора; координаты окон приходят в физических пикселях.
- **Невидимые окна.** `EnumWindows` возвращает много служебных и скрытых окон
  (в том числе «спрятанные» приложения UWP) — нужна фильтрация.
- **Полноэкранные игры и видео.** Оверлей стоит автоматически скрывать.
- **Режим «не засыпать содержимое окон».** Зависит только от рамок окон и
  переносится без изменений.
